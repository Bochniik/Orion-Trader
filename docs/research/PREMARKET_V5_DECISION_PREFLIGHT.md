# Premarket V5 Decision Preflight

Status: research validation safety gate. This does not modify runtime prediction behavior, calibration profiles, thresholds, risk policy, broker integration, or order paths.

## Purpose

Premarket V5 decision-grade validation must not run merely because a CSV exists or because one audit passes. The exact dataset must satisfy both independent requirements:

1. **Provenance:** the dataset is content-addressed back to the recorded Alpaca 1-minute raw source and collection manifest through the accepted dataset builder lineage.
2. **Readiness:** the dataset has valid prediction-time identity, premarket timestamps, feature coverage, target labels, no cross-open target leakage, and enough sessions for the preregistered 40-day train + 10-day calibration + 5-day test policy.

`scripts/run_premarket_v5_decision_preflight.py` composes those gates without weakening either one. `decision_grade_validation_allowed=true` only when both reports return `PASS` and both the dataset CSV and its dataset manifest have immutable SHA-256 identities.

## Content-addressed handoff to validation

A passing audit is not sufficient if the validator can later be pointed at different bytes. The preflight contract therefore records:

- SHA-256 of the exact dataset CSV;
- SHA-256 of the exact dataset lineage manifest;
- the complete provenance and readiness reports that authorized the research step.

`scripts/run_premarket_v5_validation.py` requires an explicit `--preflight` artifact. Before invoking the event-nested validator it recomputes the dataset and manifest hashes and requires exact equality with the preflight identities. A missing, failed, unsupported or stale preflight fails closed before model evaluation begins.

The validation runner now writes its validation manifest **before** any promotion-review gate is evaluated. The manifest binds the exact validation report to the dataset, preflight, target contract and material validation code. This ordering removes the former circular dependency where the validation manifest also attempted to contain the already-generated gate hash.

The evidence chain is therefore strictly ordered:

`raw collection -> dataset manifest -> dataset -> PASS preflight -> event-nested validation -> validation manifest -> research gate -> pipeline manifest`

The evidence pipeline routes through this chain automatically; it no longer has a decision-grade path that can skip the preflight or validation-manifest binding.

## Executable target contract

Decision-grade validation has exactly one source of truth for supported Premarket V5 horizons: `PREMARKET_TARGETS` from `scripts/premarket_directional_v4_common.py`. The runner, evidence pipeline, event-nested validator and research gate must all consume that same contract.

The current shared contract is:

- `premarket_5m`
- `premarket_15m`
- `premarket_30m`

A previous orchestration default also listed `premarket_60m`, even though the event-nested validator did not support that target. That mismatch made the default decision-grade orchestration non-executable and could also force the research gate to reject otherwise complete reports for a target the validator could never produce. The orchestration and gate now derive their targets from the shared contract instead of maintaining independent lists.

Decision-grade runs fail closed on subsets, supersets, reordered lists or unknown targets. A future new horizon must first be added to the shared model/validator contract and receive its own tests; it cannot become decision-grade merely by editing an orchestration CLI default.

## Content-addressed execution identity

Binding the dataset is not sufficient if the exact validation code is ambiguous. The audited validation manifest therefore also fingerprints the material source files that can affect Premarket V5 event-nested results, including the runner, validator, walk-forward helper, V4/V5 feature/model helpers, research gate and the underlying feature contract. It records:

- SHA-256 for every declared material validation source;
- repository Git SHA when available;
- the exact supported-target list;
- an `execution_identity_sha256` derived from the runner version, validator identity, targets and sorted source fingerprints.

If a declared material source is missing, validation fails before model evaluation. Changing a material source changes the execution identity, so evidence generated by different code cannot silently appear to be the same experiment.

## Content-addressed handoff to research review

`scripts/evaluate_premarket_v5_research_gate.py` no longer accepts a validation report by itself for decision-grade review. It requires the corresponding validation manifest and independently verifies:

- the validation report SHA-256;
- exact `PREMARKET_TARGETS` membership and order;
- the decision-grade target contract and validator identity;
- the validation `execution_identity_sha256` by recomputing it from the manifest material;
- the SHA-256 of the research-gate implementation itself against the version fingerprinted during validation.

Only after those checks does it evaluate Brier/log-loss improvement, pooled directional accuracy, signed return and fold stability. The gate output records the validation-report hash, validation-manifest hash, validation execution identity and a derived `decision_evidence_identity_sha256`. A report changed after validation, a substituted manifest, a forged execution identity or a different gate implementation therefore fails closed before eligibility metrics are considered.

This gate still authorizes only **research promotion review**. It cannot activate a runtime model, change thresholds or place trades.

## Fail-closed behavior

A missing/tampered lineage artifact, unsupported collector/builder contract, unreadable CSV, malformed prediction-time fields, target leakage, insufficient session coverage, stale preflight, dataset/manifest change after preflight, target-contract mismatch, missing material validation source, changed validation report, invalid execution identity or mismatched research-gate source blocks the decision-grade chain. A failure in one gate cannot be overridden by success in another.

The preflight report embeds both underlying audit reports so the blocker remains diagnosable and reproducible. It also hard-codes `runtime_modified=false` and `promotion_authorized=false`: passing preflight authorizes only the next research step, not deployment.

## Next step after PASS

Only the exact content-addressed dataset referenced by a passing preflight may proceed to Premarket V5 event-nested validation. The resulting report must first be bound into the validation manifest, and the research gate must then verify that exact evidence identity. Only evidence that survives the full chain may be considered against Issue #3's proper-score, calibration, fold-stability and baseline requirements before any later promotion proposal is considered.
